### Migrate v4 events to v5

The migration copies **published events in all locales**, including cover and
inline images, from `https://cms.pzkogrodek.cz` to
`https://cms-new.pzkogrodek.cz`. Markdown and HTML `content` are converted into
Strapi Blocks. Slugs are generated by v5 and are not copied or verified.
The first run can match existing events by source **slug + locale**, including
drafts. Subsequent runs use saved **source ID to target documentId** mappings;
translations stay together under one v5 `documentId`.

Before applying:

- Back up the target database and uploads, and pause editing on both instances.
- Configure all source locales on v5. Use scoped API tokens with source event
  `find` and populated image/localization read access, and target event
  `find`, `findOne`, `create`, `update`, plus upload `find` and `upload` access.
  Check that the target token can read drafts as well as published events.
- Supply `STRAPI_V4_API_TOKEN` and `STRAPI_V5_API_TOKEN` through the process
  environment. Do not put tokens in source code or command-line arguments. The
  script does not read `.env` files. Node.js 20+ and installed dev dependencies
  are required.

```powershell
yarn migrate:events
# Review the read-only plan first. This command is the only write-enabled mode:
yarn migrate:events --apply
```

Keep and back up `.migration-state\events.json` alongside your target backups.
It is git-ignored and contains CMS URLs and ID/locale mappings, not tokens.
Use `STRAPI_MIGRATION_STATE` to select another state file, and reuse that same
file for every run against the same CMS pair. Do not delete it to retry:
generated slugs cannot reliably identify previously created documents.
If a previous migration created an event before this state file existed, record
its source ID mapping manually before applying, unless its slug still matches.

Other optional environment variables: `STRAPI_V4_URL`, `STRAPI_V5_URL`, and
`STRAPI_MEDIA_ORIGINS` (comma-separated trusted CDN origins for source images).
By default only images on the old CMS origin are downloaded. Downloads must be
public, return an image MIME type, be at most 20 MiB, and not redirect. API tokens
are never sent with media downloads. Review external URLs before allowing them.

The preview fetches events and checks conversions, matches and image origins,
but does not download images or test write permissions. Unsupported structures
(such as tables, embedded video, complex quotes, and custom
list numbering) fail explicitly instead of silently losing content. Correct
the source content before retrying. Supported formatting includes headings,
paragraphs, links, lists, quotes, code, bold, italic, underline and strikethrough.
Both migrations ignore HTML style attributes and discard `<style>` elements.
Semantic formatting such as `<strong>` and `<em>` is retained; CSS-only
formatting is not converted to Blocks formatting.
Nested links become one link using the first nonempty `href` (outermost first)
and all their text and semantic formatting. Anchors without any `href` retain
their text without a link; separate sibling links stay separate.
Inconsistent shared fields between translations and conflicting
target document/slug mappings also stop the migration.

Apply uploads images before writing events, publishes each migrated locale, and
reads it back to verify the content, excluding the cover image relation.
Uploads keep the original media name (or the decoded URL filename for inline
images); no migration prefix or content hash is added. Strapi still controls
the physical storage filename. Existing media is reused by name, so different
images with the same name can reuse the wrong file; resolve name collisions
before migrating. Files uploaded by the earlier hash-naming version are not
automatically renamed or reused by the new names.
Reruns update events using the saved ID mappings.
Do not run two migrations concurrently. This is **not a transaction**:
failures can leave uploaded media and already migrated events in v5. Fix the
reported issue and rerun, or restore your backup and the corresponding state.
Each write is marked `pending` on disk first. Its returned document ID is saved
before content verification. A timeout, lost response or state-save failure
leaves an uncertain outcome and blocks reruns rather than creating duplicates.
Inspect the target event and reconcile the state before clearing `pending`.
For example, a confirmed created event with source ID 42 and locale `pl` needs
`"42": { "documentId": "TARGET_DOCUMENT_ID", "locale": "pl" }` in `documents`.
Only clear an unmapped pending creation after confirming no target was created.
Mapped target documents that are missing also stop the migration for review.

Only fields in the event schema other than slug are copied; source IDs are saved
locally, not copied into v5. The REST migration assigns new audit timestamps;
restore the original `createdAt`, `updatedAt` and `publishedAt` with the
PostgreSQL repair command below after all content migrations. Existing matching drafts are
overwritten and published. Shared fields (dates, location flag and cover image)
can also affect other target translations of that document. Ordinary links are
made absolute against the old CMS, not rewritten to guessed v5 routes. The
script does not delete unrelated target events or images.

Offline migration tests: `yarn test:migration`.

### Migrate v4 pages to v5

```powershell
yarn migrate:pages
# After reviewing the preview and backing up the target:
yarn migrate:pages --apply
```

Uses the same CMS URLs, token variables, published-only/all-locales selection,
image naming and download limits as the event migration. Grant equivalent
source and target **page** permissions, including reads of nested component
media and event relations. No live migration is run by installing the script.

Page `content` is a dynamic zone, not a single Blocks field:

- `page.page`: converts Markdown/HTML `text` to Blocks, including inline images.
- `page.gallery`: copies its media array with original names and order.
- `page.youtube`: retains the URL.
- `page.event-detail`: connects the migrated event document using the event
  migration's saved ID mapping. Strapi resolves localized relations in the
  page's locale, so the event must be published in that locale. Migrate
  referenced events and their translations first.

A legacy plain rich-text `content` string is wrapped in one `page.page`
component. Unknown components or unsupported source shapes stop the preview.
Source component IDs are not copied. The v5 schema requires a title,
description and cover image. Source slugs are not preserved: page creation
supplies a title-based slug candidate to satisfy validation, and the v5
lifecycle generates the final slug. Existing target slugs are left to v5.
Cover and gallery media relations are not verified on readback; text, component
order, YouTube URLs and event relations are verified.

Pages use **`.migration-state\pages.json`**, separate from events. Override it
with `STRAPI_PAGE_MIGRATION_STATE`; use `STRAPI_EVENT_MIGRATION_STATE` to point
to the existing event state file if it is not `.migration-state\events.json`.
The event command's `STRAPI_MIGRATION_STATE` variable is not used by the page
command. State files are bound to both CMS URLs and the content type, so they
cannot be accidentally reused between events and pages. Existing legacy event
state files remain supported.

All backup, pending-write recovery, name-collision and partial-migration
warnings above also apply to pages. Keep both state files.

### Restore original creation, modification and publication dates (PostgreSQL)

Run this **after all event/page content migrations**, including those already
completed. Strapi's normal update lifecycle overwrites `updatedAt`, so restoring
audit dates requires a final database update rather than another REST update.

```powershell
yarn migrate:timestamps
yarn migrate:timestamps --write
# After reviewing the generated SQL and selecting the NEW CMS database:
psql --dbname=NEW_CMS_DATABASE -v ON_ERROR_STOP=1 -f .migration-state\restore-timestamps.sql
```

`migrate:timestamps` is read-only by default. `--write` generates (or replaces)
`.migration-state\restore-timestamps.sql`; it **does not connect to PostgreSQL or
execute the SQL**. The `psql` command must be run in an environment configured
to connect to the new CMS PostgreSQL host, user and database. Use your normal
secure database authentication; do not put passwords in command arguments.

The generator reads the original dates from v4 using `STRAPI_V4_API_TOKEN` and
the existing source/target CMS URL settings. It uses saved mappings, not slugs,
and requires both event and page state files by default. Use `--type events`
or `--type pages` for only one collection; `--schema NAME` selects a schema
other than `public`. Custom state paths use `STRAPI_EVENT_MIGRATION_STATE`
(or the event command's `STRAPI_MIGRATION_STATE`) and
`STRAPI_PAGE_MIGRATION_STATE`. Keep v4 unchanged during migration and repair;
the dates are read from its current records, not a historical snapshot.

Back up the target database and pause writes before executing the SQL.
It updates `created_at` and `updated_at` on matching `document_id` + `locale`
rows in `events`/`pages`, covering both drafts and published versions.
It also restores `published_at` on published rows; draft rows keep NULL
publication dates and remain drafts. Regenerate any previously exported SQL
with `--write` to include the original publication dates.
All repairs run in one transaction, with row-count checks and timestamp
verification. Missing/ambiguous target records or missing published versions
abort the transaction. No content, slugs or media values change.
Inspect the dates in Strapi after applying. Later edits, publishing or content
migration reruns can change audit dates again; perform the repair last.
